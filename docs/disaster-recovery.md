# ft\_transcendence — Disaster recovery

Backups of the app database and of the file bucket, and how to put them back (INF-14, INF-15, module M14). Owner: byul-byul (PO + DevOps). Services and volumes are listed in the [Infrastructure](infra/infrastructure.md) doc.

## TL;DR

- **What:** every day at 03:00 Asia/Dubai, the `backup` service writes a `pg_dump -Fc` of the app database (`POSTGRES_DB`) and a full copy of the bucket `files` (videos, avatars, logos) into the named volume `backups`. Each copy is verified before it is kept. The 7 newest copies of each are kept.
- **Now:** `make backup` writes one at once and prints its status; `make backup-list` lists the copies.
- **Restore:** `make restore BACKUP=latest` (or a timestamp from `make backup-list`). It asks first; `RESTORE_YES=1` skips the question.
- **Check:** `make backup-check` (also in CI).
- **Not covered:** a copy on another machine. The backups live on the same Docker host as the data: they protect against a broken or deleted volume, a bad migration or a mistaken delete, not against losing the machine. See Same-host limitation.

## What is backed up

| Data | Where it lives | Backup | Why |
| --- | --- | --- | --- |
| App database `POSTGRES_DB` (accounts, profiles, chats, jobs, applications, games, video records, `alembic_version`) | `db-data` volume | `db/db-<ts>.dump`: `pg_dump --format=custom` of that one database | The data of the users. Custom format: compressed, read with `pg_restore`, which can drop and recreate each object. |
| Bucket `files` (intro videos, avatars, company logos) | `minio-data` volume | `files/files-<ts>/`: `mc mirror` of the whole bucket, one full directory per run | The files the database rows point to. Database and files of the same run share one timestamp, so a restore puts back a matching pair. |

`<ts>` is the UTC start time of the run, `yyyymmddThhmmssZ` (for example `20261119T091324Z`). Names carry no project name. The volume also holds `status`: time, result and sizes of the last run.

```text
/backups/
  db/db-20261119T091324Z.dump
  files/files-20261119T091324Z/avatars/4/e30ab65e-….png
  files/files-20261119T091324Z/users/4/intro/ebd4a1d8-….mp4
  status
```

## Not backed up, and why

| Data | Why not |
| --- | --- |
| Test database `POSTGRES_TEST_DB` | Test data only; `make test` and the fixtures recreate it. |
| Redis (`redis-data`) | Short-lived state: the Celery queue, rate-limit counters, `/ws` tickets and presence. After a restore, users log in again and open sockets reconnect. Queued Celery messages are lost; a video waiting for moderation keeps its `pending` status in the database. |
| Prometheus (`prometheus-data`) | Metrics of the last 30 days. They describe the old machine, not user data, and start again from zero. |
| Grafana (`grafana-data`) | The datasource and both dashboards are provisioned from `infra/grafana/` in Git. The admin password comes from `.env`. Only sessions and failed-login records would be lost. |
| Mailpit inbox | A test inbox inside the container, by design without a volume (INF-05). |
| `.env` and `infra/proxy/certs/` | Not in a volume. The certificate is regenerated by `make`. `.env` holds the secrets (database password, `JWT_SECRET`, MinIO keys) and is kept by the operator; see Secrets below. |
| Vault (`vault-data`, after INF-12) | See Vault follow-up. |

## How it runs

- **Service:** `backup` in `docker-compose.yml`, built from `infra/backup/Dockerfile`. The final stage is the pinned `db` image (`imresamu/postgis:15-3.4@sha256:44d4…`), so `pg_dump` and `pg_restore` match the server's major version (15). `mc` is copied from the pinned `minio` image. No new external image; `make images-check` reads both `FROM` lines. The service runs as its own non-root user (uid 10002) and publishes no port. Only this service mounts the `backups` volume.
- **Schedule:** a `bash` loop, not cron. It runs one backup a day at `BACKUP_TIME` (`HH:MM`, default `03:00`), read in the container's time zone, `TZ=Asia/Dubai`. The card's `BACKUP_CRON` became `BACKUP_TIME`: there is no cron daemon in the container to read a cron line. No backup is taken when the container starts. When the machine sleeps through `BACKUP_TIME`, the loop runs the backup as soon as it wakes. When the stack is down at that time, that day has no backup.
- **Settings:** `BACKUP_TIME` and `BACKUP_KEEP` in `.env` (`.env.example`, Backups section). An existing `.env` gets both on the next `make` (`init-env.sh` adds missing keys).
- **One run** (`backup.sh run`, the same for the schedule and `make backup`):
  1. Takes a lock, so a `make backup` during the scheduled run (or a restore) waits for it.
  2. Database: `pg_dump --format=custom` into `db-<ts>.dump.partial`, then verified:
     - `pg_restore --list` succeeds;
     - the list names every app table of the database (the tables of schema `public`, without PostGIS's own `spatial_ref_sys`);
     - `pg_restore --file=/dev/null` reads the whole archive to the end.

     The last check matters. The table of contents sits at the start of the file, so `--list` alone still passes on a dump whose last bytes are missing (tested: 100 bytes cut, `--list` exit 0; the full read fails).
  3. Files: `mc mirror` of the bucket into `files-<ts>.partial/`, then the number of files is compared with the number of objects in the bucket. A second pass runs when they differ (an upload during the first).
  4. Only a verified copy is renamed to its final name. A copy that fails stays as `.partial`, the run reports `result=FAIL`, and `make backup` exits 1.
  5. Retention (below).
  6. Writes `status`.
- **Retention:** after each run, the newest `BACKUP_KEEP` (7) complete copies are kept, separately for database dumps and for bucket copies, and older ones are deleted. Copies are ordered by the timestamp in the name, not by file dates. A `.partial` older than a day is a leftover of an interrupted run and is deleted; a younger one may belong to a run in progress and stays.
  - With one run a day, 7 copies cover one week.
  - Retention counts copies, not days. On days without a backup (stack down), the oldest copy is older than 7 days. Extra `make backup` runs push old copies out sooner.
- **Disk space:** 7 database dumps plus 7 full copies of the bucket, so about 7 times the size of the bucket. Each bucket copy is complete, with no deduplication between days. On 2026-11-19 a copy of the test stack was 83 KB of dump and 878 KB of files.
- **Health:** the loop touches `/tmp/heartbeat` every minute, also while it waits. The health check wants it younger than 3 minutes, so a stuck loop turns the container unhealthy. Whether the last backup succeeded is in `/backups/status`, not in the health state. `make backup` prints it, with the next scheduled run.
- **Logs:** start, end, file names, sizes, object counts, retention removals. Never a credential or a row of data.

### Secrets

The service reads the credentials it needs from its environment, as the other services do:
- `PGPASSWORD` (from `POSTGRES_PASSWORD`);
- `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`, which `mc` gets through `MC_HOST_store`, never on a command line.

INF-13 moves these secrets from `.env` to Vault; the `backup` service then reads them from there like the api.

A dump holds no database roles or passwords (`pg_dump` of one database, not `pg_dumpall`). After a restore onto a new volume, the database password is the one in `.env`. Without `.env`, `make` generates new secrets. The data still restores, but every login token signed with the old `JWT_SECRET` is invalid, so users log in again. Whoever runs the stack keeps a copy of `.env` somewhere safe, off the machine, never in Git.

### Vault follow-up (INF-12, INF-13)

Once Vault runs in server mode, its data lives in the `vault-data` volume and its unseal keys and root token in `scripts/vault-keys.local` (git-ignored). Neither is in this backup today.

INF-12 decides how both are kept:
- a copy of `vault-data` made while Vault is sealed or stopped;
- `vault-keys.local` stored off the machine, separately from that copy: whoever holds both can read every secret.

Until then, the secrets in `.env` are what a restore needs.

### Same-host limitation

The `backups` volume is on the same Docker host and disk as `db-data` and `minio-data`. It protects against:
- a deleted or corrupted volume;
- a migration that broke data;
- a mistaken delete in the app;
- `docker compose down -v`.

It does not protect against:
- losing or wiping the machine;
- a broken Docker Desktop disk image;
- `make fclean`, which removes the `backups` volume too.

The production step is an off-machine copy: after each run, copy the newest pair (or the whole volume) to other storage. By hand:

```bash
docker compose cp backup:/backups/. ./offsite-backup/   # then move that folder off the machine
```

The folder holds personal data (Privacy Policy section 6): keep it encrypted and access-controlled, and delete copies older than 7 days there too. To restore from such a copy, put it back into the volume with `docker compose cp ./offsite-backup/. backup:/backups/`, then `make restore`.

## Restore

`make restore BACKUP=<timestamp|latest>` puts one run back, database and files of the same moment. `BACKUP` takes `latest`, a timestamp from `make backup-list`, or a dump name (`db-20261119T091324Z.dump`). It works on the old data and on new, empty volumes.

What it does (`infra/backup/restore.sh`, then `make`):

1. Starts only `db`, `minio` (with `minio-init`, which creates the bucket and its policy on a new volume) and `backup`. The api is not started. On a new database volume, the api's migrations would otherwise create empty tables before the restore.
2. Resolves `BACKUP` to a complete pair and shows it, then shows what will be replaced and asks for `yes`. `RESTORE_YES=1` skips the question. Without a terminal and without `RESTORE_YES=1`, it stops before changing anything.
3. Stops `api` and `worker`, the services that write.
4. Database: `pg_restore --clean --if-exists --no-owner --single-transaction` into `POSTGRES_DB`:
   - `--clean --if-exists` drops each object of the dump if it exists, then recreates it. This works on the existing database and on the empty one the `db` image creates on a new volume, which already has the PostGIS extensions.
   - `--no-owner` gives every object to `POSTGRES_USER`.
   - `--single-transaction` makes it all or nothing.

   Afterwards it checks that PostGIS is present and prints the number of app tables and users and the `alembic_version`.
5. Bucket: `mc mirror --overwrite --remove` of the files copy into the bucket. Objects that are not in the copy are deleted, so no file is left without its row. The object count must then equal the copy's.
6. `make` starts the rest. The api runs `alembic upgrade head` on the restored database. A copy from an older version of the code gets only the newer migrations; a copy from the same version gets none.
7. Prints the next checks.

When a step fails, the script stops there, prints why and leaves the api stopped. Fix the cause (for example `make logs s=backup`) and run it again. A failed database step has changed nothing (single transaction).

**Content types.** `mc mirror` to a directory keeps only the bytes. On the way back, MinIO sets the `Content-Type` from the file extension. The api writes only `.png`, `.jpg`, `.webp` and `.mp4` keys, so avatars and logos come back as `image/…` and videos as `video/mp4`. Checked in the restore test below.

**Restore by hand** (the same steps, for one part only), from the repository root:

```bash
docker compose up -d --wait db minio backup
docker compose exec -T backup backup.sh list
docker compose --profile '*' stop api worker
docker compose exec -T backup backup.sh restore-db 20261119T091324Z      # database only
docker compose exec -T backup backup.sh restore-files 20261119T091324Z   # bucket only
make
```

Restoring only one of the two leaves rows and files from different moments: a video record without its file, or files nobody points to. Restore both unless the other side is known to be intact.

### After a restore

- Everything written after the backup time is gone: accounts, messages, uploads. Users log in again (the Redis sessions and tickets are new).
- Everything deleted after the backup time is back: an account deleted since is active again, a deleted video is listed again. Whoever restores checks what was deleted since the backup (support requests, the deletion log of the app once it has one) and deletes it again. The Privacy Policy promises that deleted data leaves the backups within 7 days, and a restore must not undo a deletion for longer.
- The next checks that `make restore` prints:

```bash
make https-check files-check mail-check   # routes, /files, the sign-up email
make backup-check                          # a new backup of the restored state
make logs s=api                            # no migration error
```

Then log in with an account that existed at the backup time: the profile shows its values, the avatar shows, and the intro video plays under My Videos.

## Checks

`make backup-check` (`infra/backup/smoke-test.sh`, in the CI `stack` job) runs against the running stack and prints one `ok` / `FAIL` line per check:

1. The `backup` container is healthy, runs as a non-root user, and has `BACKUP_KEEP` = 7.
2. `make backup` exits 0 with `result=ok`, and its copy is the newest complete one. On an empty bucket (CI), one probe object is uploaded first and removed at the end.
3. The newest dump passes the same verification as a run (every app table listed, read to the end).
4. The newest files copy has as many files as the bucket has objects. One object, the first by name, has the same sha256 in the copy and in the bucket.
5. Retention on a test directory inside the container. It gets 9 fake old copies of each kind, a `.partial` of two days ago and a fresh `.partial`. Afterwards exactly 7 copies of each kind must remain (the 7 newest), the old `.partial` must be gone and the fresh one kept. The expected 7 is fixed in the check, so a service started with another `BACKUP_KEEP` fails it.
6. The `backups` volume:
   - the container publishes no host port;
   - no other container mounts the volume;
   - the proxy serves no backup content at `/backups/…`, `/db/…` or `/files/../backups/…` (no `PGDMP` dump, no `status`).
